# ADR-001: Technologia UI: Tauri 2 vs GPUI

- **Status:** proponowany
- **Data:** 2026-11-05
- **Issue:** #8

## Kontekst
Conductor UI to cienki klient daemona `conductord` (PLAN.md, rozdz. 3). W UI mieszczą się edytor (tree-sitter, LSP, multibuffer), terminale per agent, diff review z akceptacją per hunk, tablica przebiegów i skrzynka zgód. Wybór technologii UI musi spełniać wymagania z planu:

- **W1 / W3 (bezpieczeństwo, offline):** UI nie może niczego ładować z sieci. Nie ma CDN, zdalnych fontów, telemetrii ani auto-update z internetu. Dystrybucja odbywa się przez podpisane paczki z wewnętrznego rejestru.
- **W4 (wydajność):** metryka sukcesu z rozdz. 8 to otwarcie repozytorium o 1 mln linii w < 2 s i opóźnienie wpisywania < 16 ms (jedna klatka przy 60 Hz).
- **Zespół i harmonogram:** 4–6 osób, w tym 2–3 Rust i 1–2 frontend. Faza 1 (MVP) trwa 6–8 tygodni, a jej wynikiem ma być działający terminal, diff review i prosty edytor.
- **Licencje:** nie forkujemy Zed (GPL-3.0 / AGPL-3.0). Z jego ekosystemu bierzemy tylko biblioteki na licencjach permisywnych.
- **Platformy:** Linux jest platformą pierwszej klasy, macOS i Windows są wymagane od fazy 2.

Plan zakłada Tauri 2 na MVP i punkt decyzyjny w sprawie GPUI na koniec fazy 2. Ten ADR sprawdza to założenie i określa, jak mierzalnie podjąć decyzję w tym punkcie.

## Rozważane opcje
1. **Tauri 2 + TypeScript + CodeMirror 6 + xterm.js.** Webview systemowy, backend Tauri w Rust jako most do `conductord`.
2. **GPUI (Apache-2.0).** Natywny UI renderowany na GPU, jak w Zed. Edytor, terminal (na bazie `alacritty_terminal`) i multibuffer piszemy sami.
3. *(odrzucona wstępnie)* **Electron.** Ma ten sam model webowy co Tauri, ale dołącza własnego Chromium (~100+ MB), więc rośnie powierzchnia ataku i koszt aktualizacji. Jedyna zaleta to identyczny silnik na wszystkich OS. Wracamy do niej tylko wtedy, gdy różnice między webview systemowymi okażą się blokujące (zob. ryzyka).
4. *(odrzucona)* **Fork edytora Zed.** Wykluczony przez licencję GPL-3.0 i liczbę ścieżek komunikacji z chmurą (PLAN.md, rozdz. 2).

## Porównanie

### Stan rozpoznania (zweryfikowane vs założenia)
Stan sprawdzony 2026-11-05, pobieżnie:
- **Zweryfikowane:** GPUI żyje w monorepo Zed (`crates/gpui`, Apache-2.0). Na crates.io dostępne są nieoficjalne republikacje śledzące tagi wydań Zed (np. `gpui-unofficial`, `gpui-kit`) z dopiskiem, że nie są utrzymywane przez Zed Industries. Nie znalazłem stabilnego, wersjonowanego wydania GPUI od Zed z gwarancją zgodności API.
- **Założenie (do weryfikacji w spike'u):** API GPUI zmienia się bez semver i bez okresu deprecjacji, razem z potrzebami Zed. Dokumentacja to głównie przykłady w repo i kod samego Zed. Ekosystem komponentów (np. biblioteki widgetów stron trzecich) istnieje, ale jest młody.
- **Założenie:** Tauri 2 jest stabilny od wydania 2.0 (2024). Model capabilities/permissions i izolacji IPC działa tak, jak opisuje dokumentacja Tauri 2. Wiedza pochodzi z dokumentacji i doświadczenia, a nie z testu w naszym środowisku.
- **Założenie:** liczby wydajnościowe niżej są szacunkami inżynierskimi. Zastępuje je benchmark z sekcji „Punkt decyzyjny”.

## Decyzja
**Wybieramy Tauri 2 + TypeScript + CodeMirror 6 + xterm.js na MVP (fazy 1–2).** GPUI zostaje opcją docelową z formalnym punktem decyzyjnym na koniec fazy 2, rozstrzyganym benchmarkiem opisanym niżej.

Uzasadnienie:
1. **Wąskim gardłem MVP nie jest rendering, tylko orkiestracja.** Wartość fazy 1 to worktree, sandboksy, egress guard, audyt i diff review. Wydajność edytora na poziomie Zed jest wymogiem W4, ale nie jest kryterium wyjścia fazy 1.
2. **Czas i ludzie.** GPUI przeniósłby budowę edytora, terminala i multibuffera na tych samych 2–3 programistów Rust, którzy budują `conductord`. To realnie zagraża harmonogramowi fazy 1. Tauri pozwala pracować równolegle osobom frontend i Rust.
3. **Bezpieczeństwo jest do opanowania w obu opcjach**, choć różnymi metodami. GPUI ma mniejszą powierzchnię ataku. Tauri ma za to wymuszoną CSP i capabilities oraz dobrze zrozumiany model zagrożeń. Przy założeniu, że UI jest cienkim klientem bez uprawnień (autoryzację wykonuje daemon), kompromitacja webview nie daje więcej niż to, na co pozwala API daemona dla sesji UI.
4. **Ryzyka GPUI są organizacyjne, nie techniczne.** Brak oficjalnych wydań i stabilnego API, szczątkowa dokumentacja i sąsiedztwo kodu GPL to koszty, które rosną z czasem utrzymania. Warto je ponieść dopiero wtedy, gdy pomiar pokaże, że Tauri nie spełnia W4.

Uczciwie: jeśli celem byłby wyłącznie edytor klasy Zed, GPUI wygrałby wydajnością. Przegrywa na czasie, kompetencjach i stabilności zależności, a te w obecnym planie ważą więcej.

### Odwracalność: UI jako cienki klient `conductord`
Żeby wybór UI był odwracalny, obowiązują zasady:
- **Cała logika w daemonie.** Worktree, agenci, PTY, polityki, audyt, LSP, indeks, wyszukiwanie, obliczanie diffów i stan buforów współdzielonych z agentami są w `conductord`. UI tylko wyświetla i zbiera intencje użytkownika.
- **Jeden kontrakt: JSON-RPC 2.0 po lokalnym sockecie** (unix socket na Linux/macOS, named pipe na Windows), uwierzytelniony tokenem sesji wydanym przez daemon i uprawnieniami pliku/pipe'a. Schemat API jest wersjonowany i opisany formalnie (np. JSON Schema lub typy generowane z Rust do TS), a testy kontraktowe działają niezależnie od UI.
- **Strumienie zamiast odpytywania.** Wyjście PTY, zdarzenia przebiegów, prośby o zgodę i zmiany bufora przychodzą jako subskrypcje. Wyjście terminala to surowe bajty (base64 lub kanał binarny), żeby nie zależeć od formatu xterm.js.
- **Backend Tauri jest tylko mostem.** Komendy Tauri przekazują wywołania do socketu daemona i nie zawierają logiki biznesowej. Webview nigdy nie dostaje bezpośredniego dostępu do systemu plików ani shella.
- **Bufory po stronie daemona.** Model dokumentu (rope + CRDT na potrzeby edycji wspólnej z agentami) żyje w `conductord`. UI trzyma tylko kopię roboczą i synchronizuje operacje. Dzięki temu edytor GPUI mógłby zastąpić CodeMirror bez zmian w daemonie.
- **Zakaz logiki w TypeScript, której nie da się przenieść.** Reguły akceptacji hunków, polityki, wyliczenia diffów i parsowanie wyjścia agentów są w Rust. Kod TS ogranicza się do prezentacji.

Przy tych zasadach migracja na GPUI oznacza przepisanie warstwy prezentacji, ale nie daemona ani protokołu. Możliwe jest też podejście hybrydowe (np. natywne okno edytora w GPUI obok Tauri), choć nie jest ono planowane.

### Punkt decyzyjny (koniec fazy 2): benchmark
Benchmark uruchamiamy w CI na wewnętrznej infrastrukturze, na referencyjnych maszynach dla każdego OS: „typowy laptop firmowy” (np. 4 rdzenie, 16 GB RAM, zintegrowane GPU) oraz jeden profil VDI/VM bez akceleracji GPU. Wyniki to mediana i p95 z co najmniej 20 powtórzeń.

**Korpus:**
- R1: syntetyczne repozytorium ~1 mln linii w ~10 tys. plików (mieszanka Rust/TS/Java), generowane deterministycznie z ziarna.
- R2: duże prawdziwe repozytorium open source (np. kopia jądra Linux w lustrze wewnętrznym) dla nawigacji i wyszukiwania.
- F1: pojedynczy plik 1 mln linii (~40 MB). F2: plik z liniami po 10 tys. znaków (minifikowany JS).

**Scenariusze i progi (Tauri musi spełnić wszystkie na Linux, macOS i Windows):**

| # | Scenariusz | Metryka | Próg |
|---|-----------|---------|------|
| B1 | Otwarcie R1: od komendy do interaktywnego drzewa plików i pierwszego pliku z podświetlaniem | czas | p95 < 2 s |
| B2 | Otwarcie F1 i przewinięcie na koniec | czas do pierwszej klatki / czas skoku | < 2 s / < 100 ms |
| B3 | Wpisywanie w F1 i w pliku z 20 aktywnymi dekoracjami inline diff od 3 agentów | input-to-paint latency (znacznik czasu zdarzenia klawiatury do prezentacji klatki, mierzony instrumentacją i kamerą o wysokiej częstotliwości na próbce) | p95 < 16 ms, p99 < 33 ms |
| B4 | Jak B3, przy jednoczesnym strumieniu z 8 terminali agentów (każdy ~1 MB/s wyjścia) | input-to-paint latency, utracone klatki | p95 < 16 ms, < 1% klatek > 33 ms |
| B5 | Przewijanie multibuffera z 200 fragmentami z 50 plików (diff review) | czas klatki | p95 < 16,7 ms |
| B6 | Wyszukiwanie projektowe w R2 i wyświetlenie 10 tys. wyników | czas do pierwszych wyników / do pełnej listy | < 200 ms / < 2 s |
| B7 | Zużycie pamięci UI po 1 h scenariusza mieszanego (otwarte R1, 8 terminali, 3 diffy) | RSS procesu UI (+ procesy webview) | < 1,5 GB, wzrost < 10% w ostatnich 30 min |

**Reguła decyzji:**
- Tauri spełnia wszystkie progi na wszystkich OS: **zostajemy przy Tauri**, a GPUI wraca na stół najwcześniej w fazie 4.
- Tauri nie spełnia B3, B4 lub B5 na co najmniej jednym OS po jednej iteracji optymalizacji (np. przeniesienie podświetlania do daemona, kanał binarny IPC, ograniczenie dekoracji): **uruchamiamy spike GPUI** (2–3 tygodnie, 1–2 osoby). Spike ma zaimplementować minimalny edytor (otwarcie F1, wpisywanie, podświetlanie tree-sitter z daemona) i widget terminala, przejść B2–B4 i oszacować koszt pełnej migracji.
- Migrujemy, jeśli spike spełnia progi z zapasem ≥ 30% i ocena kosztu mieści się w budżecie fazy 3/4. Wtedy powstaje ADR zastępujący ten.
- Niezależnie od wyników sprawdzamy stan GPUI: czy istnieje oficjalne, wersjonowane wydanie, jak często łamie się API (liczba breaking changes w ostatnich 6 miesiącach) i czy jest dokumentacja. Brak oficjalnego wydania zwiększa wymagany zapas wydajności, bo rośnie koszt utrzymania.

## Konsekwencje

**Pozytywne**
- Najkrótsza droga do MVP fazy 1. Frontend i Rust pracują równolegle.
- Dojrzałe komponenty (CodeMirror 6, xterm.js, merge view) na licencjach MIT/Apache-2.0, bez ryzyka GPL.
- Wymuszona CSP i capabilities Tauri 2 dają weryfikowalny brak ruchu sieciowego z UI.
- Kontrakt IPC z daemonem robi z UI wymienną warstwę. Ułatwia to tryb zdalny (faza 3) i ewentualną migrację na GPUI.

**Negatywne**
- Zależność od trzech różnych webview systemowych. WebKitGTK na Linux to najsłabsze ogniwo wydajnościowe, a to akurat platforma pierwszej klasy.
- WebView2 na Windows wymaga decyzji Evergreen vs Fixed Version oraz zablokowania jego własnych połączeń sieciowych.
- Bufor i podświetlanie w JS z kopią w daemonie oznaczają podwójną pamięć i koszt synchronizacji przez IPC.
- Ryzyko, że W4 (< 16 ms) nie zostanie osiągnięte przy wielu agentach i dekoracjach, a migracja na GPUI będzie wtedy dużym projektem.

**Do zrobienia**
1. Szkielet aplikacji Tauri 2 z capabilities ograniczonymi do jednej komendy-mostu i ścisłą CSP. Test CI: brak `http(s)://` w paczce poza allowlistą, brak pluginów `http`/`shell`/`updater`.
2. Specyfikacja i wersjonowanie API JSON-RPC `conductord` (osobne issue), generowanie typów TS z Rust, testy kontraktowe.
3. Test egress UI na każdym OS (ruch sieciowy procesu UI i webview przy pracy offline = 0 połączeń poza localhost).
4. Uzgodnienie z działem IT polityki WebView2 (Evergreen przez WSUS/Intune vs Fixed Version z wewnętrznego rejestru) i minimalnej wersji WebKitGTK na wspieranych dystrybucjach Linux.
5. Harness benchmarku B1–B7 i korpus R1/R2/F1/F2, uruchamiane cyklicznie od fazy 1, żeby trend był znany przed punktem decyzyjnym.
6. Reguła `cargo-deny` blokująca licencje GPL/AGPL (istotna, jeśli spike GPUI dojdzie do skutku).
